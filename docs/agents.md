# Agents and company policy

Mango exposes a marketer's native operations through `/mcp`. Discovery lives at `/.well-known/oauth-protected-resource/mcp`; the supported MCP versions are `2026-07-28` and `2025-11-25`. The signed-in **Agents** page shows policy, agent activity, pending approvals and reviews. An agent cannot use its token to change policy or Pause.

Business connects a person by their durable Business ID through signed settings. A matching email address grants no authority. Each request re-reads that person's current Mango role. Owner-only connections and erasure stay owner-only. Contacts retain the person's native visibility restrictions. Installation, imports, credentials and provider callbacks keep their existing doors and purposes.

The company chooses autonomous, review, approval or blocked behavior for each class. With no current policy, an unanswered class, an expired policy or Pause, agent effects stop. Approval shows a server-built summary bound to the saved native evidence. Only the named eligible person can decide it. Changed content, sender evidence or native revisions require a new decision. Agent authorization is recorded as **agent for person**; real approvers remain separate.

For a newsletter, read `mango.store.read`, `mango.sender.read`, `mango.audience.read` and the relevant contact or segment records. Create a private draft with `mango.campaigns.create`. `mango.campaigns.update` takes the **native revision ID** in `id`; save canonical content and structured audience rules. Refresh checks with `mango.campaigns.checks_refresh`, then request `mango.campaigns.authorize` for that exact campaign and revision. The normal scheduler prepares recipient work and dispatches it through separate typed actions. Each delayed action rechecks agent authority and policy. Inspect `mango.delivery.read` and campaign results afterward.

Native safeguards still apply: confirmed consent must cover the exact sender and message category; suppression, dormancy, frequency and sender evidence govern admission. A later opt-out excludes that recipient. A stale draft or lapsed sender cannot send. An uncertain provider handoff remains uncertain and is never blindly resent. Provider acceptance does not prove inbox delivery or readership. Imported engagement does not become Mango delivery or causal revenue.

Other registered families cover private templates, reusable blocks and media; proposals and paid design artifacts; contacts and segments; supported store synchronization; sender metadata and connection changes; report schedules; public archive publication; signup behavior; and native access changes. `tools/list` is the current typed catalogue. Resources expose current records and redacted operation receipts, with private reads subject to policy. Resource text from contacts, imports and providers is untrusted. Secrets, receipt tokens and credentials are not ordinary resources.

Design generation uses the configured provider and retains its actual artifact. Choosing a design does not authorize, schedule or send a campaign. Generic flow graphs remain private drafts with no message transport. Only the supported WooCommerce tag-and-exit starter can run; it sends no messages. Mango does not supply a general lifecycle sender, paid-ad experimentation or category-wide autonomous optimization.

Tool results describe native outcomes, including skipped recipients and uncertain or refused provider work. Use an `idempotency_key` on mutations and retain it for an exact retry; changed arguments conflict. Use `expected_revision` when supplied by the workflow. The event feed retains access-filtered resource changes and a cursor.

Shared spend caps are currently **not enforced**. Native provider quotas and admission rules still apply. Provider cost alone is not money moved, and an agent result is not a claim that a budget reservation or payment occurred. This integration remains subject to the complete production conformance and contract acceptance gates; the catalogue is not a claim that every configured provider has passed them.
