# Mango operations

Pinned rer **0.2.22** selects and acquires Node **22.20.0** and pnpm **10.12.4** and installs locked dependencies; neither tool needs a separate manual install. All application lifecycle commands use the installed `@runeditrun/rer` package pinned exactly to **0.2.22**; `rer` selects that checkout's CLI, and package scripts invoke the same command; start with [Run it locally](AGENTS.md#run-it-locally). `describe --json` reports verbs/flags, `check --profile first-party` validates structure without configuration, and `doctor` diagnoses tools and missing inputs without provider requests or private values.

The newsletter profile needs email only. Commerce, SMS, AI and design generation are optional: leave each disabled group absent; partial enabled groups fail with missing names. `verify` runs contract/source checks, operations tests, typecheck, production build and local browser journeys. Run affected tests while editing; CI is the complete wall. Local success does not prove hosted operation or delivery.

## Source provenance

`edition.json`, `base-copies.json` and `sources.lock.json` identify maintained Base source and the selected immutable revision. `pnpm run source:check` verifies integrity; `pnpm run source:lock` refreshes it after intentional source changes. Mango owns its adapter and contact-authority recovery. The CLI package pin and copied runtime source revision are separate: upgrading the installed CLI does not replace the retained Base auth/mail source under `src/vendor/base`. Only `/auth/setup-complete` imports operator-auth from the installed package for its local completion handshake; ordinary email access continues through the retained runtime source. The installed package supplies both the CLI and deploy kit; neither is vendored in Mango. The shared rer deploy kit is the only deployment implementation. Selected unchanged runtime copies remain byte-exact; portability journal, import and copy handling are Mango adaptations with immutable Base origin mappings. Local guides and reduced environment/diagnostic helpers are adaptations. Base owns its omitted standalone tests and fixtures.

## Authentication

Base operator-auth owns native sessions, one-use confirmed magic links, operator authority versions and last-active-operator protection. Every operator has equal product powers. Setup declares optional `oidc-provider@1` with cardinality 1 through `IDENTITY_PROVIDER`, registering `/auth/oidc/auth/callback` and `/auth/oidc/auth/logout`; leaving it empty retains email-link sign-in. `/auth/setup-complete` delegates only the local completion handshake to the pinned Base package, which requires the local CLI proof and an active owner; production cannot use it. Migration 0043 adds Base authentication settings without rewriting existing operator/session tables. Local setup claims one first owner and stops its temporary application without requesting a sign-in email. Repeat setup keeps the saved private settings and existing owner, but rer 0.2.22 runs the build, migrations and temporary application again without requesting a sign-in email. It is not read-only: authentication records and SQLite runtime files can change, as do build outputs, command receipts and redacted diagnostic logs. Omitting --port reuses the saved origin. Configuration generators and resolved deployment declarations write only when their contents change. Production builds use wrangler.production.toml; local dev, preview and migrations use wrangler.toml. Building or repeating a deploy dry-run with unchanged inputs preserves both configuration files and private settings; build outputs, receipts and diagnostic logs may be regenerated. Dev’s automatic sign-in creates real authentication records. Submitting Mango’s email sign-in form explicitly captures a message in the local application outbox; setup and dev do not request that message automatically. Dev prints readiness after its health checks and signs in automatically through its private `RER_OPEN` link. In rer 0.2.22, `--login` uses that same dev identity flow and `rer outbox` is retired; Mango’s key-protected `/__dev/outbox` application route still retains local captures. `rer preview` serves a fixed build of the local worker (`.seed/preview`) over the same local state and sign-in as dev; Mango's production entry never serves the development outbox, so preview cannot serve the built server folder. Preview runs no schedules, and `build` leaves the local `wrangler.toml` in place so dev works afterwards.

`/signin` accepts an HTML POST before hydration. Link GET/HEAD renders a confirmation form without consuming it; the affirmative POST creates the native cookie. Private documents, APIs and Start server functions validate the session independently. Local outbox routes are restricted to the configured loopback origin, never exposed on a deployment. Viewing messages only reads storage; expired captures are removed on a subsequent capture. No email provider is required locally. Messages and token-bearing links must never appear in command logs.

Apply migrations in filename order. Preserve attribution profiles, invitation cancellation records, Base triggers, bootstrap admission and operator-version history. Cancelling an invitation invalidates its links and leaves durable inactive admission state; reactivation cannot revive it. Settings distinguishes pending and active operators and reloads after removal conflicts.

Hosted configuration uses canonical `OWNER_EMAIL`, `SESSION_SECRET`, `SETUP_TOKEN` and HTTPS origin. A separately selected compatibility binding profile uses `INITIAL_OPERATOR_EMAILS`, `SESSION_SIGNING_KEY` and `AUTH_SETUP_TOKEN`; conflicting authorities are refused. Keep independent random keys and exact private backups. Owner admission is an explicit authenticated operation, never inferred from a push or command name.

## Mail and sender authority

Managed hosting includes mail without a provider account or an owner-supplied provider API key. Run Edit Run provisions `MAIL_PROVIDER=rer`, the sender in `MAIL_FROM`, the HTTPS relay endpoint in `MAIL_RELAY_URL` and a private relay credential in `MAIL_API_KEY`. Keep that credential server-side; it is supplied by Run Edit Run, not copied from a SendGrid or Resend account.

Managed relay mail covers sign-in and subscription confirmations. Newsletter sending still needs a verified business sender, reply-to and unsubscribe headers, and delivery evidence from an own-provider connection; the current relay does not provide these newsletter features.

This selected provider is the Managed mail exception to BASE-DATA-005 in CONTRACT.md. RER receives only the recipient, subject, text and optional HTML, with the private credential authenticating the request. Mail depends on active Managed access and a valid credential; revocation or service failure is an owner-visible delivery problem. Free and Assisted hosting retain their independent own-provider connections.

Free and Assisted hosting use your own provider. Select `MAIL_PROVIDER` in `deploy.json` `vars` (`sendgrid` in this checkout, or `resend`), and set the verified sign-in sender in `MAIL_AUTH_FROM`. `MAIL_PROVIDER_API_KEY` supplies that provider's key. `MAIL_WEBHOOK_SECRET` is optional with SendGrid: when set it is the base64 SPKI ECDSA public verification key of its signed Event Webhook, and without it deployment and sending work while delivery status stays **Accepted** (never **Delivered**) and `/webhooks/mail/sendgrid` rejects every request. Add it later with `rer deploy --environment NAME --set-secret MAIL_WEBHOOK_SECRET` (value from the environment or `--env-file`). For Resend both `MAIL_WEBHOOK_SECRET` (the existing Svix signing secret) and `MAIL_WEBHOOK_ID` are required. Transactional auth uses Base mail directly. SendGrid newsletter submission also uses Base mail; its delivery correlation metadata is **not** deduplication.

For a separately authorized installation, configure SendGrid's signed event webhook at `https://<deployment>/webhooks/mail/sendgrid`. Incoming original bytes are verified by Base before normalization; supported facts persist through Mango's existing inbox, destination suppression and conflict/replay safeguards before success. Submissions, processed events and delivered events remain distinct. SendGrid uses the approved single-attempt policy; uncertain handoffs require operator review and never automatically retry. Sender authority requires provider/DNS verification and the approved trusted receiver's original evidence. Configure the account-level webhook setting separately and verify live events before relying on delivery evidence. Sender lease, consent, saved revision and approval checks are unchanged. Resend keeps its existing marketing transport/reconciliation contract; it does not inherit claims from Base transactional mail.

Receiver material must come from an authenticated original-message mailbox connector. Excerpts, provider domain state and DNS alone cannot manufacture receiver authentication proof. Configure both `MAILBOX_RECEIPT_URL` and `MAILBOX_RECEIPT_RECIPIENT` (the deploy kit stores both as Worker secrets) to select the authenticated production receiver connector and its diagnostic recipient. One-sided configuration rejects deployment before the build and also rejects Worker startup. Leave both unset to keep the receiver off. Set `MANGO_TEST_EMAIL_ALLOWLIST` to a comma-separated list containing the receiver address and every permitted QA destination; with no explicit allowlist the owner address is the only test destination. The installation trusts this public HTTPS endpoint to provide authoritative original-message receipt evidence; neither value has an owner-specific default.

## Deployment

`rer deploy --environment production --dry-run` validates/builds locally without provider requests. The installed, pinned rer 0.2.22 deploy command provisions the Worker, automatically claims the first owner through native bootstrap, then removes the one-time setup token from the Worker. Mango forwards the managed-owner contract to rer, so rer owns the first claim and token retirement. Repeat deployment keeps the existing owner. These are the deploy command responsibilities; local dry-run evidence does not certify hosted provisioning, owner claim, token retirement or provider delivery. The following recipe supplies the actual deploy inputs for Free and Assisted hosting with your own provider; Managed hosting supplies its relay mail configuration through Run Edit Run. No separate owner claim command is required.

1. Create a private deployment input file once, from the repository root:

```sh
node --input-type=module <<'NODE'
import { mkdirSync, readFileSync, writeFileSync } from 'node:fs';
import { randomBytes } from 'node:crypto';
mkdirSync('.rer', { recursive: true, mode: 0o700 });
const values = { MANGO_DEPLOY_ENV: 'production', ...Object.fromEntries(['SESSION_SECRET', 'SETUP_TOKEN', 'CONTACT_HASH_SALT'].map(name => [name, randomBytes(32).toString('hex')])) };
const deployment = JSON.parse(readFileSync('deploy.json', 'utf8'));
for (const name of ['CLOUDFLARE_ACCOUNT_ID', 'CLOUDFLARE_API_TOKEN', ...deployment.secrets.map(input => input.environment)]) values[name] ??= '';
// Deployment and sender verification read product settings directly from deployment.vars.
writeFileSync('.rer/hosted.env', Object.entries(values).map(([name, value]) => `${name}='${value}'`).join('\n') + '\n', { flag: 'wx', mode: 0o600 });
NODE
```

2. Edit `.rer/hosted.env` privately. Choose `MANGO_DEPLOY_ENV` for this installation (the generated value is `production`). Fill the account ID, scoped API token, owner email, SendGrid API key, verified sign-in sender (`MAIL_AUTH_FROM`), optional signed-webhook verification material (`MAIL_WEBHOOK_SECRET`, optional with SendGrid; Resend needs it and `MAIL_WEBHOOK_ID`), and, optionally, initial allowed link hostnames (`MANGO_ALLOWED_LINK_HOSTS`). Leaving hosts empty uses the app’s assigned host; change them later in Mango Settings. Keep the generated authority values. Values are shell single-quoted: escape an embedded apostrophe as `'\''`. Never print this file or commit it. Sender display name, reply-to and postal address are saved in the app's sender setup after sign-in.

   Sender evidence needs no deployment input: after sign-in, Settings sends a one-time check to the operator's own address and the operator confirms it from that inbox. Receiver verification through a connector is optional. Leave its two lines empty to keep it off, or fill **both** `MAILBOX_RECEIPT_URL` and `MAILBOX_RECEIPT_RECIPIENT` (its diagnostic mailbox). The URL must have the form `https://<public-receiver-host>/receipts?token=<private capability>`, using the trusted connector's public DNS hostname, the exact `/receipts` path and exactly one query parameter named `token`. Replace both placeholders with the connector's actual settings; this template is not a usable endpoint. Use its nonempty private capability (at most 4096 decoded characters), URL-encoding the value so reserved characters cannot introduce extra parameters. Do not include a custom port, URL user information, a fragment or whitespace. IP addresses and local/private hostnames are unsupported. The connector must implement the supported Cloudflare Email Routing receipt semantics; a generic mailbox API URL is not sufficient. Keep the entire token-bearing URL private in this file; the deploy kit stores both receiver settings as Worker secrets. Never paste the URL into logs, screenshots, client configuration or shared reports.

   `MANGO_TEST_EMAIL_ALLOWLIST` is optional: active operators can always send tests to their own sign-in addresses. Fill it with extra comma-separated test addresses, and with the receiver's address when a connector is configured. This allowlist may also be configured without a receiver; it never grants sign-in access. The receiver alone cannot verify provider/DNS authority, and without receiver evidence the owner's inbox confirmation in Settings is the sender evidence. Optional design generation uses the pair described below.

3. Set `storeTimezone`, `organizationName` and `landingSummary` in `src/ext/config.ts`, then commit that edit locally. Commit other intentional tracked edits, including changes to `deploy.json`, before deploying; deploy refuses uncommitted tracked changes. No push is needed. Keep private inputs untracked:

```sh
git add src/ext/config.ts
git commit -m "Configure Mango installation"
```

4. From that committed checkout, load those inputs and deploy:

```sh
set -a
. ./.rer/hosted.env
set +a
rer deploy --environment "$MANGO_DEPLOY_ENV"
```

After a successful health check, deploy claims the first owner without printing credentials and removes the one-time setup token from the Worker. A repeat keeps the existing owner. If claiming fails, deploy reports that the application is deployed but owner admission failed; repeat the same deploy after resolving the reported cause. Open the deployed origin, request an email sign-in link for `OWNER_EMAIL`, confirm it, and complete sender setup. Preserve matching private session and contact authority backups.

The kit uploads only the inputs in `deploy.json`: required secrets are needed on first deploy and inherited afterwards. Receiver and QA inputs, like design inputs, are optional secrets uploaded when supplied; the kit preserves existing Worker secrets on later uploads even when their shell inputs are absent. `.rer/declarations/` contains names only. To change an existing secret deliberately, replace that Worker secret using your authorized Cloudflare administration; rer deploy keeps existing values. Product settings (provider, app version, timing and rate limits) are defined once in `deploy.json` `vars`, consumed by both deployment and the sender-verification runner; change them there and deploy before verification. Shell values do not override those declared settings. `MANGO_PUBLIC_BASE_URL` comes from the successful deployment receipt, after its project, environment, Worker, owned D1 and canonical HTTPS workers.dev origin have been checked. The runner refuses a conflicting shell origin. Keep the receipt and private inputs for the same installation together.

To sign in as the hosted owner without email (lost mail or a mistyped owner address), load the same inputs and run `rer signin --environment "$MANGO_DEPLOY_ENV"`: it prints a single-use link for the recorded owner, valid for 15 minutes and recorded in the owner's audit log. To remove a deployment and everything rer created for it (Worker, D1, R2, Queue), run `rer deploy --environment "$MANGO_DEPLOY_ENV" --remove --yes`; rer reads back that each is gone and touches nothing else. Export data first if you want to keep it.

For an update, preserve private inputs, the deploy receipt and your data backups, then run:

```sh
git pull --ff-only
set -a
. ./.rer/hosted.env
set +a
rer deploy --environment "$MANGO_DEPLOY_ENV"
```

Choose the same `--environment` as the first deployment. Verify existing and fresh email sign-in and the Worker health after deployment. rer installs updated locked dependencies and keeps the owner automatically. Mango never reads Wrangler credential files.

Names derive from project and environment: `mango-production`, `mango-production-db`, `mango-production-assets-bucket` and `mango-production-mango-jobs`. The kit derives the workers.dev origin from the authenticated account, owns resources and migrations, uploads Worker/assets and verifies bindings plus source/version health after a real D1 ping.

Restore mode on a deployment: set `"MANGO_RESTORE_MODE": "1"` in `deploy.json` `vars` and deploy; product routes and the queue consumer pause (product requests answer 503 `restore_in_progress`). Cron records each actual tick as blocked by restore; sign-in, `/health` and the authenticated transfer routes stay open. Set it back to `"0"` and deploy again after the restore. A hosted restore itself is not yet proven.

Back up `.rer/deploy/<environment>.json`; repeat deployment requires matching ownership state. Same-named unowned resources are refused. Resolve uncertain resource ownership with the Base deploy-kit recovery guide (`modules/deploy-kit/README.md` in the installed `@runeditrun/rer` package), preserving source and data. CI verifies application changes. The Run site workflow automatically publishes marketing pages and documentation; application deployment remains explicit.

## Scheduler readiness

The schedule and results page reads durable actual Worker scheduled entries. A fresh installation reports no tick observed and explains that Cloudflare is starting the schedule. Approval also queues each step due within 12 hours as a Queue message delayed to its exact time, so a first letter leaves on time before the first tick; the step is fenced, so the later Cron dispatch adds nothing. The every-minute schedule is observed only after its Worker handler runs; deploy, approval, health checks and page reads do not establish it. A tick older than fifteen minutes is overdue. Its latest completion, failure or restore/erasure block is separate from that observation. Expired send windows remain closed regardless of scheduler readiness. The actual entry time is separate from Cloudflare’s nominal scheduled slot: a delayed callback records when it really entered Mango. A late completion cannot replace a newer entry’s outcome, including across Worker restarts. A completed tick confirms scheduling checks, never provider acceptance or delivery.

## Authored newsletter draft API

An authenticated same-origin POST `/api/campaigns` accepts `{ "composition": <draft fields> }`. Required fields are name, email subject/body/text, sender name/from/reply-to/address, message category, audience description, structured inclusion rule and one or more timezone-resolved steps. Links and exclusions are optional. All content, steps and the operator attribution are inserted atomically in draft state; this request cannot approve, schedule or send.

A mail-only inclusion rule may use `{ "version": 1, "operator": "all", "predicates": [{ "sourceType": "contact", "field": "emailStatus", "comparator": "eq", "value": "subscribed" }] }`. Contact fields are limited to id, email, displayName, emailStatus and smsStatus. These are recorded contact data, not commerce facts. Derived source requirements omit contact fields but continue to require every commerce predicate's real source. Consent, dormancy, suppression, frequency, frozen-candidate and dispatch checks still apply. Source requirements are derived by the server, not trusted from request JSON.

The response supplies `campaignId` and `revisionId`. Read `/api/campaigns/:id`, save with PATCH `/api/campaign-revisions/:revisionId`, recompute via POST `/api/campaigns/:id/checks` with `{revisionId}`, and approve via POST `/api/campaigns/:id/approve` with `{revisionId,idempotencyKey}`. Approval remains fail-closed on missing sender/provider evidence.

Campaign images (CAMP-012): an authenticated same-origin POST `/api/campaign-assets` takes one JPEG, PNG, GIF or WebP file as the single `file` part of a `multipart/form-data` body. The type is read from the file's own header (the declared type and name are ignored) and a truncated file is refused; byte and pixel limits are `maxCampaignAssetBytes` and `maxCampaignAssetPixelsPerSide` in `seed.json`. The file is stored once in `ASSETS_BUCKET` under `campaign-assets/<sha256>` with a `campaign_assets` record that cannot be changed or deleted (contact erasure can still remove bytes that hold an erased contact's identifier; `/media/` then answers 410); a repeat upload answers 200 with the existing image, a new one 201, and both give its public `url`. GET/HEAD `/media/<sha256>` (also with the stored type's extension, `/media/<sha256>.png`) is a declared public path: no session or cookie, exact type, `nosniff`, immutable cache, and `mediaRequestsPerMinutePerAsset` per image (429 above it). It records nothing about requesters. In HTML mode the email editor's **Insert image** uploads through the same route. Approval verifies these images in D1 and R2 rather than fetching the deployment's own hostname. Every image fetch from an inbox is a Worker request and one D1 row write, which counts toward the Free plan's daily quotas.

Design import (DESIGN-004): in a draft's email editor, **Import 12ui design** takes a LayerDoc version 2 file and the PNG candidate it was converted from, both made with the owner's own `12ui` CLI (`12ui draft …`, then `12ui convert <candidate.png> --engine api --output layerdoc --model fast`). The browser crops the photos, uploads them through `/api/campaign-assets` and builds the body as an unsaved edit; saving, preview and approval are unchanged. Import itself uses no 12ui key and makes no request to 12ui; only the optional design generation below does, with its own declared external. On a local review copy the origin is `http:`: an imported email saves and previews with its styling and, on request, its own images, but approval and test sends refuse its `http:` images until the deployment has an HTTPS public base URL. See docs/first-newsletter.md.

Design generation (DESIGN-001 to DESIGN-003) is optional and off by default. To let operators press **Design with 12ui** in a draft's email editor, set both `DESIGN_PROVIDER_API_KEY` (the owner's own 12ui API key, a secret) and `DESIGN_PROVIDER_ORIGIN` (`https://12ui.com`); one without the other fails startup, and an origin that is not a bare HTTPS origin is refused. With both absent Mango constructs no design adapter and never contacts 12ui. On a hosted deployment set both as environment inputs when you run `deploy`: `deploy.json` declares them as optional secrets (`"optional": true`), which `deploy` uploads only when their inputs are set, on the first deploy or a later one, and keeps afterwards (Mango resolves `deploy.json` into `.rer/declarations/` for the deploy kit, with the optional secrets you set); `rer verify` checks the build without them. Setting them with `wrangler secret put` also works. On a copy running on your computer, add both lines to `.dev.vars` and restart dev; that copy may also name a loopback `http://127.0.0.1:<port>` origin for a stand-in service. A run spends from the owner's 12ui account (about $0.03 per candidate and $0.05 per layout at 12ui's list prices, free within its daily allowance) and writes `external_cost_facts` rows with provider `12ui`. Runs live in `design_jobs` and `design_candidates` (migration 0040; migration 0041 adds why and until when a run waits on 12ui) and in R2 under `design-jobs/<run>/`; they are exported like everything else. The queue command kinds are `design.draft` and `design.layout`, and the `* * * * *` cron fails runs past their 15-minute deadline. A 429 with `Retry-After` makes a run wait (the editor shows the time until Mango asks again); a 429 without one, a 402, a refused key or three failed passes fail it at once with Mango's reason, and every request to 12ui has a time limit, so a silent 12ui fails a run within minutes. Downloads from 12ui are read with a size limit and follow a redirect only on the configured origin, so the key never goes to another host. What is sent to 12ui and its sub-processors is declared in `seed.json → externals → design-provider` and CONTRACT.md.

## Public signup protection

Signup iframe access uses the persisted exact-origin allowlist in signup settings. The list starts empty, so other origins cannot embed signup until an operator explicitly allows them. Same-origin signup remains available.

Optional Turnstile requires public variable `TURNSTILE_SITE_KEY` and secret `TURNSTILE_SECRET_KEY` together. Configure the widget for the hostname of `MANGO_PUBLIC_BASE_URL`. The challenge script loads only after a trusted keyboard or pointer interaction with the signup form. Verification sends the challenge token and visitor IP to Cloudflare. The form uses action `newsletter-signup`; Siteverify must affirm both action and hostname within five seconds, or signup rejects before storage. Without either key the form has no challenge. With only one key startup fails.

All installations require a complete saved sender identity before capture. Signup uses the trusted `CF-Connecting-IP` header, rejects invalid addresses and groups IPv6 by /64 (including equivalent spellings), with IPv4-mapped addresses sharing IPv4 allowances. Persistent atomic limits are five attempts per network per UTC hour, three reservations per destination per UTC day and fifty reservations globally per UTC hour. Failed or duplicate concurrent reservations may consume capacity; restart cannot reset it. Confirmation GET/HEAD only render the affirmative POST form. Public signup never mails or changes a subscribed, opted-out, suppressed or erased opted-out destination. Explicit reconsent requires a separately recorded authorized ledger flow.

## Local state and credential recovery

Durable local D1/R2 state is `.wrangler/state`; private `.dev.vars` records local format 2 with `OWNER_EMAIL`, `AUTH_ORIGIN`, `SESSION_SECRET`, `SETUP_TOKEN`, `CONTACT_HASH_SALT` and `MANGO_LOCAL_HASH_AUTHORITY=contact-salt-v1`. CLI state is `.rer/local`; installer work is `.seed/installer`. Keep the exact database/assets and matching settings together in private backup; credentials are 0600. Stop every local writer before recovery, build, transfer or reset.

An ambiguous database at `src/core/app/client/.wrangler/state` is refused without modification. If canonical state is absent, make `.wrangler` and explicitly move the verified matching database there. If both exist, preserve both and identify the matching backup before choosing; never combine or discard them by name.

`pnpm run auth:rotate -- --force --owner-email EMAIL --port PORT` is explicit credential recovery, separate from setup. It preserves verified contact authority while rotating login/setup credentials, invalidates prior sessions, and requires a fresh outbox sign-in. Setup never converts unknown settings or guesses authority. For unversioned settings proven to use the session key for contact hashes, add `--legacy-session-authority`; for settings proven to use the independent salt, add `--legacy-contact-authority`. These mutually exclusive options require `--force`. Preserve the original backup. If the effective key is uncertain, restore a known matching backup; hashes cannot reconstruct it. Missing/unknown authority fails closed; adding a version marker is not recovery.

## Declared mail loop

For Free and Assisted hosting, OPERATIONS v2 declares the maintained SendGrid newsletter path explicitly. Supply `MAIL_PROVIDER=sendgrid`, the runtime `MAIL_PROVIDER_API_KEY`, and `SENDGRID_API_KEY` for Base's declarative mail-loop inspection. Both key names identify the same account credential; the second is used only by the shared inspector. For example, assign it privately with `export SENDGRID_API_KEY="$MAIL_PROVIDER_API_KEY"`; this prints neither value.

Resend remains supported for Free and Assisted hosting. To select it, explicitly change the transactional-mail loop's provider to `resend` in OPERATIONS.json, replace its environmentSources key with RESEND_API_KEY, set MAIL_PROVIDER=resend and supply RESEND_API_KEY from the same credential as MAIL_PROVIDER_API_KEY. Refresh the source lock with `pnpm run source:lock` after changing the descriptor. An inconsistent declaration fails inspection; no provider is selected automatically. Local installation uses the development outbox and needs neither hosted provider key.

Shopify source observations and sync receipts are retained until explicit erasure or owner-directed data management; scheduled maintenance does not expire them automatically. They are history, not independent consent or delivery authority.

## Complete data export and restore

With dev stopped, `rer export --output exports/mango.jsonl` creates a new private archive. It contains every product D1 table and original R2 asset with metadata: contacts, consent, surviving opt-outs, source records, campaigns/revisions, approvals, outcomes, settings, audit and import history. Attribution profiles carry no login authority. Auth sessions/tokens, owner-claim admission, outbox, transfer bookkeeping, secrets/provider credentials and queue transport envelopes and installation-local scheduler observations are excluded. Remote CLI targets are unsupported and fail visibly.

Back up matching private settings separately, including contact and signing authority. The archive binds restoration to their fingerprint and cannot recover them. Copy the archive and private settings into a new empty local destination with no writer running, then run `rer import --input exports/mango.jsonl --yes`. The shared CLI locks state, applies migrations and validates/stages data before atomic restoration; wrong schema, integrity, key fingerprint or nonempty destinations are refused. Re-export to a new filename and compare content before ordinary setup and fresh sign-in. Reconfigure provider inputs separately; never rotate authority during restore.

The authenticated transfer API enforces maintenance: product reads/writes and scheduled work stop, queue jobs retry, and only health/auth/transfer remain available. Erasure retires current snapshots and advances a source-wide epoch floor without retaining per-row hashes. Every older archive is refused against a known local floor or supplied current matching authority, even if it contains no erased row. Upgrade 0044 raises all known source floors, removes legacy journals and transfer metadata, and queues dynamic copies and unfinished transfer objects for idempotent retirement before application or native transfer work. Nonempty legacy journals are refused before staging. Native CLI restore enforces locally known floors; supplying current authority on a fresh destination uses the authenticated HTTP restore API. A cold offline destination cannot infer future erasure from an old archive alone. Offline backups remain subject to owner retention/privacy policy.

`rer reset --non-interactive` prints the local removal inventory and refuses deletion. Review it, then use `reset --yes` for explicit destruction of local data, owners, settings, outbox and command/installer state. It refuses active operations, preserves source/dependencies, exports and deploy receipts, and permits fresh empty setup. Export first if retaining data.

### Optional open estimates

Open tracking is off by default. In Insights, an authenticated operator can enable **Privacy-sensitive open estimates**. This installation-wide setting persists in D1 and affects future marketing email preparation. Mango adds its own signed first-party pixel; provider open tracking remains disabled. Disabling stops recording from every existing pixel; re-enabling never reactivates old pixels. Counts represent recipient-step image-load estimates, may include proxies and automation, and never establish reads or affect delivery, clicks, conversions, confidence, attribution or deliverability. Private tokens and facts are retained until contact erasure removes them. Tokens stop accepting requests after 30 days.

### Scheduled dispatch

Production declares Cron every minute in `deploy.json` and `deploy/wrangler.template.toml`. Approval persists future steps; Cron discovers due work before optional source synchronization and reconciliation and enqueues native Queue commands. Due-now approval also enqueues immediately. Recipient leases and durable step identities prevent duplicate dispatch; a command cannot start before its stored resolved UTC instant. Scheduler readiness becomes overdue after three missed minute slots.

The local go-live proof uses an independent wall-clock driver reading the deployment's cron declaration because its Vite fixture does not initiate Cron callbacks. It exercises the production scheduled export, native D1 and Queue, substituting only provider network edges. This proves local scheduling behavior; hosted Cron activation and Cloudflare latency require separate evidence.
